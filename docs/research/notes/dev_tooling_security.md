## A1. Which CLI tools measurably help agents, and why they appear in CLAUDE.md/AGENTS.md setups

### Takeaway
The commonly recommended core set is ripgrep, fd, ast-grep, jq (+yq), gh, a task runner (just), fast package managers (uv, bun), and linters/secret scanners; the stated reasons are non-interactivity, structured (`--json`) output, small/quiet output (token efficiency), honest exit codes and speed. There is **no rigorous benchmark** showing these tools raise agent task success; the evidence is practitioner convention plus official Claude Code docs that bundle ripgrep and use jq in hook examples. Interactive TUIs (lazygit, zellij, eza/bat cosmetics) help the supervising human, not the agent.

### Cited Findings
- Claude Code itself bundles ripgrep: "Ripgrep is bundled with the native Claude Code binary"; ripgrep is also listed as a sandbox dependency in `/sandbox`'s Dependencies tab — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Bright Data's (vendor) guide, published 5 Aug 2026 / updated 18 Oct 2026, judges CLI tools for Claude Code on five criteria: non-interactive (agent can't answer prompts or drive full-screen UIs), structured output (`--json`), token efficiency (quiet modes, field selection, pagination), honest exit codes, composability. Its picks besides its own products: ripgrep, ast-grep, gh, jq, just, uv, bun, gitleaks. It states Claude Code's Grep tool is built on a bundled ripgrep, so a system `rg` matters for Bash-invoked searches. Its ripgrep "30-second grep → sub-second" example is illustrative, not a measured benchmark — [Bright Data blog](https://brightdata.com/blog/ai/best-cli-tools-for-claude-code)
- Trail of Bits' public Claude Code config (practitioner, security firm) installs `jq ripgrep fd ast-grep shellcheck shfmt actionlint zizmor uv` (+ ruff, ty, pip-audit, prek, worktrunk, cargo-deny, oxlint, agent-browser) and puts a tool table in the global CLAUDE.md: rg (replaces grep), fd (replaces find), ast-grep (AST search), shellcheck, shfmt, actionlint, zizmor (GitHub Actions security audit), prek (replaces pre-commit), wt (worktrees), trash (replaces rm; "Never `rm -rf`" enforced by hook). Rule: "Prefer `ast-grep` over ripgrep when searching for code structure; use ripgrep for literal strings and log messages." Also: "Prefer structure-aware tools (ast-grep, LSPs, compilers) over text pattern matching." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config) ; [claude-md-template.md](https://raw.githubusercontent.com/trailofbits/claude-code-config/HEAD/claude-md-template.md)
- A widely shared CLAUDE.md snippet maps task types to tools: fd for files, rg for text, ast-grep for code structure, jq for JSON, yq for YAML/XML, fzf for selection — [gist (kibotu)](https://gist.github.com/kibotu/4788d83f00f0a3991f51a043492fa8dd) (seen via search snippet only)
- Compliance caveat: a feature request reports Claude Code sometimes ignores a CLAUDE.md section telling it to use rg/fd and falls back to find/grep — [claudeissues.com #54800](https://claudeissues.com/issue/54800-feature-make-tools-like-ripgrep-and-fdfind-a-first-class-citizen)
- jq is effectively required for Claude Code hooks: the official formatter example is `jq -r '.tool_input.file_path' | xargs npx prettier --write` on a `PostToolUse` hook with an `Edit|Write` matcher — [Claude Code docs: Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Evidence on instruction files themselves: ETH Zurich/LogicStar paper (arXiv:2602.11988, 12 Feb 2026, ICLR 2026 submission) found "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average"; context files are "useful for specifying non-standard coding practices" — [arXiv abstract](https://arxiv.org/abs/2602.11988)
- Claude Code's own guidance: target under 200 lines per CLAUDE.md; move part-of-codebase rules into path-scoped `.claude/rules/`; `@imports` do not reduce context cost — [Claude Code docs: Memory](https://code.claude.com/docs/en/memory)
- Tool popularity/health (GitHub stars, shields.io, 2026-10-19): ripgrep 69k (last commit Aug), fd 45k, ast-grep 16k, jq 36k, yq 16k, gh (cli/cli) 47k, difftastic 26k, just 36k, go-task 16k, mise 35k, uv 91k, bun 96k, direnv 16k, tmux 50k, zellij 36k, lazygit 83k, eza 24k (last commit July), bat 61k, delta 33k (last commit March — slowest-moving of the set), fzf 84k — [shields.io GitHub badges](https://img.shields.io/github/stars/BurntSushi/ripgrep.json) (same endpoint per repo)

### Inferences
- The defensible rationale for each tool is structural: rg/fd are fast and .gitignore-aware; ast-grep gives syntax-aware search/rewrite (fewer false matches than regex); jq/yq shrink JSON/YAML before it enters context and power hooks; gh gives the agent scriptable PR/issue/CI access; just/task make the project's commands discoverable in one place; uv/bun cut wait time in edit-test loops; direnv/mise pin per-project toolchains and env so the agent's shell matches the dev's.
- Because the Grep/Glob tools already use bundled ripgrep, adding rg/fd to CLAUDE.md mainly helps when the agent drops to Bash; since adherence is imperfect, a PreToolUse hook that rewrites/blocks `grep -r`/`find` is more reliable than prose.
- lazygit, zellij, eza, bat, delta, difftastic are human-supervision tools (reviewing agent diffs, multiplexing sessions); none had sources showing agents benefit from them directly. `difft --display json`-style use by agents is plausible but unsourced.
- Given arXiv:2602.11988, keep tool tables short and only list non-obvious tools (e.g., ast-grep, project task runner), not things the model already uses well.

### Gaps
- No controlled benchmark found measuring agent success/latency with vs. without rg/fd/ast-grep/jq.
- No sources found specifically recommending mise, direnv, difftastic, eza or bat for agents (only star counts collected).
- Bright Data and similar listicles are vendor content; no independent replication.

## A2. Code review / QA helpers used alongside agents (AI reviewers, built-in commands, hooks, fast linters)

### Takeaway
Claude Code now has three first-party review paths: local `/code-review` (any plan), cloud `/code-review ultra` (Ultrareview), and the managed GitHub "Code Review" app (Team/Enterprise, multi-agent find→verify→rank→post, never approves/blocks). Third-party reviewers (CodeRabbit, Greptile, Qodo) have conflicting, mostly vendor-run benchmarks clustered around ~50% F1. The deterministic layer that gives agents fast feedback is hooks + fast linters/formatters (Ruff, Biome, oxlint, prek).

### Cited Findings
- Claude Code Code Review: several agents examine the diff and surrounding code in parallel, a verification step filters false positives, findings are deduplicated, ranked by severity and posted inline with a "Claude Code Review" check run; "A review never approves or blocks the pull request"; levels Quick/Standard/Deep; Team and Enterprise only; not available with Zero Data Retention/HIPAA/CMEK; `REVIEW.md` read from base/default branch, "never from the pull request's own changes"; review has read-only repo access and doesn't build/run code — [Claude Code docs: Code Review](https://code.claude.com/docs/en/code-review.md)
- Comparison table in the same doc: `/code-review` (any plan, local session), Ultrareview (cloud sandbox), Claude in your own CI via GitHub Actions/GitLab CI, or your own reviewer subagent/skill — [Claude Code docs: Code Review](https://code.claude.com/docs/en/code-review.md)
- Related first-party security tooling: `/security-review` (on-demand pass over branch changes), `security-guidance` plugin (Claude reviews its own changes during the session), `claude-security` plugin (codebase scan) — [Claude Code docs: Security](https://code.claude.com/docs/en/security)
- anthropics/claude-code-security-review GitHub Action: 6.4k stars, last commit Feb 2026 (≈8 months without commits — possibly stale) — [shields.io](https://img.shields.io/github/last-commit/anthropics/claude-code-security-review.json)
- AI reviewer benchmarks conflict: Morph (Mar 2026) CodeRabbit F1 51.5% (precision 50.5%, recall 52.5%) vs Greptile F1 50.2% (precision 66.2%, recall 40.4%); Martian 2026 independent study had CodeRabbit first of ten at 51.2% F1; Greptile's own July 2025 test claimed 82% bug catch; Qodo's Feb 2026 test gave Qodo 60.1% F1; "three benchmarks published between July 2025 and February 2026 crowned three different winners" — [Morph comparison](https://www.morphllm.com/comparisons/coderabbit-vs-greptile); [Particula](https://particula.tech/blog/greptile-vs-coderabbit-vs-qodo-ai-code-review-2026) (secondary/vendor sources)
- Hooks as deterministic feedback: PostToolUse `Edit|Write` → formatter; PreToolUse script exiting 2 blocks edits to `.env`, `package-lock.json`, `.git/` with stderr fed back to Claude; PostToolUse `decision: "block"` with `continueOnBlock: true` feeds the reason back so Claude continues fixing — [Claude Code docs: Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Trail of Bits: "Automated guardrails are the enforcement layer, not this file. Setting up linters, type checkers, formatters, and pre-commit hooks is the first step of a new project"; "Zero warnings"; hooks are "structured prompt injection at opportune times ... Guardrails, not walls"; uses PreToolUse hooks to block `rm -rf` and direct push to main; recommends the `hookify` plugin to generate hooks from plain English — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- Fast linters: Ruff "10-100x faster than existing linters (like Flake8) and formatters (like Black)" (50k stars) — [astral-sh/ruff](https://github.com/astral-sh/ruff); prek is a Rust drop-in replacement for pre-commit, "multiple times faster" (8.6k stars vs pre-commit 16k) — [j178/prek](https://github.com/j178/prek); Biome 26k stars, oxc/oxlint 23k stars, lefthook 8.9k — [shields.io](https://img.shields.io/github/stars/biomejs/biome.json)
- VS Code extension exposes language-server diagnostics to Claude via `mcp__ide__getDiagnostics` (and `mcp__claude-vscode__getDiagnostics` in the chat panel, v2.1.285+) — [Claude Code docs: VS Code](https://code.claude.com/docs/en/vs-code.md)

### Inferences
- A practical small-team stack: formatter+linter on PostToolUse (Ruff / Biome / oxlint — sub-second so they can run on every edit), type checker + tests in a Stop hook or pre-commit via prek/lefthook, `/code-review` locally before PR, one PR-level AI reviewer (Claude Code Review if on Team/Enterprise, otherwise CodeRabbit/Greptile or Claude in GitHub Actions), and humans keep merge authority.
- Benchmarks are too inconsistent to pick CodeRabbit vs Greptile on numbers; precision (noise) vs recall trade-off is the real choice.

### Gaps
- GitHub Copilot code review was not researched (no source fetched).
- Pricing for CodeRabbit/Greptile/Claude Code Review not verified (Code Review cost page not fetched).
- Biome/oxlint official speed figures not captured (READMEs had no numeric claim in grep).

## A3. Terminal and editor setup relevant to Claude Code users

### Takeaway
Claude Code works in any terminal; Ghostty, Kitty, iTerm2, WezTerm, Warp, Apple Terminal and Windows Terminal support Shift+Enter without setup, and desktop notifications fire by default only in Ghostty, Kitty and iTerm2. Practitioners (Trail of Bits) favour Ghostty. For editors: the official VS Code extension (also Cursor, Kiro, Devin Desktop via Open VSX), JetBrains plugin, and Zed/JetBrains via the Agent Client Protocol (ACP) registry with a Claude adapter.

### Cited Findings
- Shift+Enter: works without setup in Ghostty, Kitty, iTerm2, WezTerm, Warp, Apple Terminal, Windows Terminal; needs `/terminal-setup` in VS Code, Cursor, Devin Desktop, Alacritty <0.16, Zed; not available in gnome-terminal and JetBrains IDE terminals (use Ctrl+J or `\`+Enter) — [Claude Code docs: Terminal config](https://code.claude.com/docs/en/terminal-config.md)
- Desktop notifications by default only in Ghostty, Kitty, iTerm2; Warp and VS Code integrated terminal need `preferredNotifChannel: "terminal_bell"` or a Notification hook; tmux needs `set -g allow-passthrough on`, `set -s extended-keys on`, `set -as terminal-features 'xterm*:extkeys'`; OSC 7501 session-status protocol (v2.1.295+); flicker → `/tui fullscreen` or `CLAUDE_CODE_NO_FLICKER=1` — [Claude Code docs: Terminal config](https://code.claude.com/docs/en/terminal-config.md)
- `/terminal-setup` in VS Code/Cursor sets `terminal.integrated.gpuAcceleration` to "off" to prevent garbled text — same source
- Trail of Bits recommends Ghostty: native GPU rendering, "~500MB vs ~8GB for two VS Code terminal sessions", Shift+Enter works without `/terminal-setup`, built-in splits; WezTerm on Windows — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config) (practitioner claim, not benchmarked)
- Stars (2026-10-19): Ghostty 62k, Warp 66k (release v0.2026.06.03), WezTerm 29k (latest tagged release 20240203 — releases stale though commits continue, last commit Oct), tmux 50k, zellij 36k — [shields.io](https://img.shields.io/github/stars/ghostty-org/ghostty.json)
- VS Code extension: plan review/editing, auto-accept edits, @-mention files with line ranges, multiple conversations in tabs, checkpoints/rewind (fork conversation and/or rewind code), built-in IDE MCP server (`mcp__ide__getDiagnostics`; `mcp__ide__executeCode` for Jupyter always asks via Quick Pick); requires VS Code 1.94.0+; installs in Cursor and other forks (Devin Desktop, Kiro) via Open VSX — [Claude Code docs: VS Code](https://code.claude.com/docs/en/vs-code.md)
- ACP Registry launched 28 Jan 2026 by Zed with JetBrains: register an agent once, available in every ACP client; lists Claude Code, Codex CLI, GitHub Copilot CLI, OpenCode, Gemini CLI — [Zed blog](https://zed.dev/blog/acp-registry); JetBrains IDEs 2025.3.2+ install agents from the Agent Picker — [JetBrains AI blog](https://blog.jetbrains.com/ai/2026/01/acp-agent-registry/)
- Claude runs in ACP clients via an adapter: zed-industries/claude-agent-acp (the old claude-code-acp name redirects), 2.7k stars, v0.94.0, active; ACP spec repo 4.5k stars; Zed 92k stars (v1.24.3) — [shields.io](https://img.shields.io/github/v/release/zed-industries/claude-agent-acp.json)

### Inferences
- For a small team: any modern GPU terminal (Ghostty on macOS/Linux, WezTerm or Windows Terminal on Windows) plus tmux/zellij for parallel sessions is sufficient; the main Claude-specific concerns are Shift+Enter, notifications, and tmux passthrough. Warp adds its own agent features but loses default desktop notifications for Claude Code.
- Use the VS Code/JetBrains integrations when you want the agent to see LSP diagnostics and to review diffs inline; Zed via ACP gives a lighter-weight editor option but through an adapter (feature parity not verified).

### Gaps
- No independent benchmark of terminal performance with Claude Code (Ghostty memory claim is ToB's).
- JetBrains plugin feature set and Zed/ACP feature parity with the CLI not verified.
- Cursor's own agent vs Claude Code-in-Cursor trade-offs not researched.

## A4. AGENTS.md vs CLAUDE.md and cross-agent portability (Codex CLI, Gemini CLI, OpenCode, Cursor, Amp) and sync tools

### Takeaway
As of Claude Code v2.1.277+, Claude Code reads AGENTS.md natively — but by default only when there is no CLAUDE.md/CLAUDE.local.md in the tree; the simplest portable layout is a single AGENTS.md (or CLAUDE.md that `@imports` AGENTS.md). Skills are portable via the Agent Skills (SKILL.md) open standard, originally from Anthropic and now supported by Codex, Gemini CLI, Cursor, Copilot/VS Code, OpenCode, Amp, Goose, Junie and many more. For multi-agent repos, rulesync and ruler generate per-agent files; `npx skills` installs skills to many agents.

### Cited Findings
- Claude Code: with an AGENTS.md and no CLAUDE.md/CLAUDE.local.md → reads AGENTS.md; if both exist → reads CLAUDE.md only; setting `instructionFiles` (`claude-md-or-agents-md` default, `claude-md-and-agents-md`, `claude-md`, `managed-only`) under `pluginConfigs` → `cc-plugin-agents-md@builtin` (user or managed settings only; ignored in project settings); requires v2.1.277+; not read: `AGENTS.local.md`, `AGENTS.override.md`, `.agents/`; adding a personal `CLAUDE.local.md` silently stops AGENTS.md loading; `InstructionsLoaded` hooks don't fire for directly-read AGENTS.md; `/doctor prompt-audit` (v2.1.283+) audits CLAUDE.md/AGENTS.md/rules/skills — [Claude Code docs: Memory](https://code.claude.com/docs/en/memory)
- AGENTS.md is stewarded by the Agentic AI Foundation under the Linux Foundation, "used by over 60k open-source projects"; supporters listed include Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Copilot coding agent, Windsurf, Augment; nearest AGENTS.md takes precedence; OpenAI's main repo has 88 AGENTS.md files — [agents.md](https://agents.md/) (repo agentsmd/agents.md 25k stars)
- Codex: global `~/.codex/AGENTS.override.md` or `AGENTS.md`; walks git root → cwd, one file per directory (`AGENTS.override.md` > `AGENTS.md` > `project_doc_fallback_filenames`), concatenated root→cwd; `project_doc_max_bytes` default 32 KiB — [OpenAI Codex docs: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Gemini CLI: default context file GEMINI.md; `context.fileName` in settings.json accepts a list, e.g. `["AGENTS.md","CONTEXT.md","GEMINI.md"]`; all found files are concatenated — [Gemini CLI docs](https://geminicli.com/docs/cli/gemini-md/) (via search snippet)
- Agent Skills: "originally developed by Anthropic, released as an open standard"; a skill is a folder with `SKILL.md` (name + description minimum) plus optional scripts/references/assets; progressive disclosure (discovery → activation → execution); client showcase includes Claude Code, ChatGPT & Codex, Gemini CLI, Cursor, GitHub Copilot, VS Code, OpenCode, Amp, Goose, Junie, OpenHands, Roo Code, Factory, Kiro, OpenClaw and others — [agentskills.io](https://agentskills.io/)
- Codex reads Claude plugin marketplaces: "Codex supports Claude plugin marketplaces directly" (`codex plugin marketplace add trailofbits/skills`) — [trailofbits/skills README](https://github.com/trailofbits/skills)
- vercel-labs/skills (`npx skills add owner/repo`, 36k stars, v1.7.4): "The CLI for the open agent skills ecosystem", supports OpenCode, Claude Code, Codex, Cursor "and 75 more"; commands find/list/use/check/update/remove/init, experimental npm-dependency sync; directory skills.sh — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- rulesync (1.5k stars, v38.0.0, active): generates configs for many AI tools from `.rulesync/` — rules, commands, MCP, ignore files, subagents and skills; `rulesync import --targets claudecode`, `rulesync convert --from cursor --to copilot,claudecode` — [dyoshikawa/rulesync](https://github.com/dyoshikawa/rulesync)
- ruler (2.9k stars, v0.3.44, last commit Aug 2026): `.ruler/` single source distributed to Copilot, Cursor, Claude Code etc., also MCP config and skills — [intellectronica/ruler](https://github.com/intellectronica/ruler); [developertoolkit.ai guide](https://developertoolkit.ai/en/ecosystem/frameworks/rules-sync/) (secondary)
- Cross-agent CLIs (stars 2026-10-19): openai/codex 130k (rust-v0.163.0), google-gemini/gemini-cli 107k (v0.64.0), opencode 218k (v1.19.3; sst/opencode now anomalyco/opencode) — [shields.io](https://img.shields.io/github/stars/openai/codex.json)

### Inferences
- Recommended small-team layout: one `AGENTS.md` (short, <200 lines, non-obvious commands/conventions only) committed at root; no committed `CLAUDE.md` unless Claude-specific content is needed, in which case `CLAUDE.md` = `@AGENTS.md` + Claude-only bits (works in every Claude Code session, including those where native AGENTS.md support is unavailable). Warn devs that a personal `CLAUDE.local.md` disables AGENTS.md loading unless they set `claude-md-and-agents-md`.
- Put reusable procedures in SKILL.md skills (portable) rather than agent-specific slash commands; Claude-specific hooks/permissions stay in `.claude/settings.json` (not portable).
- Sync tools (rulesync/ruler) are worth it only when a team actively uses ≥3 agents; they add a generation step and a new dependency.

### Gaps
- Gemini CLI `.agents/skills` path and Amp/Cursor exact AGENTS.md precedence rules were not verified from primary docs.
- OpenAI docs page for Codex's Claude-marketplace compatibility not fetched (claim from Trail of Bits README).

## A5. Sharing a team's Claude Code setup (plugin marketplace in git, .claude/settings.json, managed settings)

### Takeaway
Three layers: (1) repo-committed `.claude/settings.json` (permissions, hooks, `extraKnownMarketplaces`, `enabledPlugins`) + `.mcp.json` + AGENTS.md/CLAUDE.md; (2) a team plugin marketplace = a git repo with `.claude-plugin/marketplace.json`, ideally pinning each external plugin to a commit `sha`; (3) managed settings (server-managed from claude.ai admin, MDM, or `managed-settings.json`) to enforce allowlists, lock auto-update, and require plugins.

### Cited Findings
- A marketplace is a directory/repo with `.claude-plugin/marketplace.json` (`name`, `owner`, `plugins[]` each with `name` + `source`); teammates run `claude plugin marketplace add <owner>/<repo>`; repo can be private; validate with `claude plugin validate` — [Claude Code docs: Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Plugin sources: relative path, `github` (`repo`, `ref`, `sha`), `url` (any git, `ref`, `sha`), `git-subdir` (sparse/partial clone), `npm` (fetched "without running install scripts"), `archive` (HTTPS zip with `sha256` integrity), `command` (runs a shell command each session). `sha` = full 40-char commit; when `ref` and `sha` both set, `sha` is checked out — [Claude Code docs: Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference)
- Repo-level: `extraKnownMarketplaces` + `enabledPlugins` in `.claude/settings.json` apply only after the contributor accepts workspace trust; plugins with external sources still need `claude plugin install <name>@<marketplace> --scope project` — [Claude Code docs: Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- Managed: `extraKnownMarketplaces` + `enabledPlugins` force-install; per-marketplace `autoUpdate` true/false (managed value can't be toggled by users); `DISABLE_AUTOUPDATER` in managed `env` stops plugin and CLI auto-update (`FORCE_AUTOUPDATE_PLUGINS=1` to keep plugins updating); release channels = two marketplaces pointing at different refs; containers/CI: `CLAUDE_CODE_PLUGIN_SEED_DIR` read-only seed with auto-update forced off; `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1` for `-p` runs — same source
- Delivery: server-managed settings (claude.ai Organization settings > Claude Code > Managed settings; Owner role), MDM plist/registry, or `managed-settings.json` (+ `managed-settings.d/` drop-ins); by default only the first source that delivers a policy key applies (server → MDM → file) unless `managedSourcesBehavior: "merge"` — same source
- Practitioner pattern: Trail of Bits keeps a public marketplace (trailofbits/skills, 7.6k stars), a private one, and `skills-curated` — "Third-party skills and external marketplaces we've vetted and approved for use. Every addition gets code review." — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)

### Inferences
- Small team without Enterprise: a private GitHub marketplace repo with every third-party plugin vendored or pinned by `sha`, plus repo `.claude/settings.json` declaring it; review changes to the marketplace repo via PR (this gives an approval gate and audit trail). With Team/Enterprise: add server-managed `strictKnownMarketplaces` + `autoUpdate: false` on external marketplaces.

### Gaps
- No public data on how many teams use pinned SHAs vs floating refs.

## B1. Documented incidents and research on malicious/compromised skills, plugins and MCP servers (2025–2026)

### Takeaway
Real-world abuse is concentrated in open skill registries (ClawHub/OpenClaw, skills.sh) and npm-distributed MCP servers; Claude Code itself had project-file RCE/key-exfiltration CVEs (fixed 2025, disclosed Feb 2026); researchers have demonstrated malicious Claude Code marketplace plugins using hooks to bypass approval, and weaponised skills (ransomware). Classic post-approval "rug pulls" remain mostly proof-of-concept.

### Cited Findings
- Tool poisoning (Invariant Labs, Apr 2025): hidden instructions in an MCP tool description made Cursor exfiltrate the user's SSH key and MCP config; GitHub MCP "toxic agent flow" (May 2025): a malicious public GitHub issue hijacks an agent into leaking private-repo data when the user asks it to review issues — no compromised tool needed — [Invariant Labs: GitHub MCP vulnerability](https://invariantlabs.ai/blog/mcp-github-vulnerability); [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-ai-agent-exfiltration-2/) (via search snippets)
- Lethal trifecta (Simon Willison, 16 Jun 2025): private data + untrusted content + external communication ⇒ exfiltration; MCP "encourages users to mix and match tools from different sources"; "The only way to stay safe there is to avoid that lethal trifecta combination entirely" — [simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- postmark-mcp (Sept 2025, discovered by Koi Security): unofficial npm package impersonating Postmark's MCP server; from v1.0.16 silently BCC'd every email to the attacker after ~15 benign releases; ~1,500 weekly downloads; described as the first malicious MCP server found in the wild — [The Hacker News](https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html); [CSO Online](https://www.csoonline.com/article/4064009/trust-on-mcp-takes-first-in-the-wild-hit-via-squatted-postmark-connector.html) (search-snippet level; Koi's original post now redirects to Palo Alto Networks)
- Rug pull classification dispute: PolicyLayer argues postmark-mcp was a compromised package, not a post-approval definition change, and found no confirmed in-the-wild rug pull against a production MCP deployment with named victims as of April 2026 — [PolicyLayer](https://policylayer.com/attacks/mcp-rug-pull) (secondary)
- Claude Code CVEs (Check Point Research, disclosed 25 Feb 2026): CVE-2025-59536 — a repo's `.claude/settings.json` SessionStart hooks ran before the trust dialog; repo settings `enableAllProjectMcpServers`/`enabledMcpjsonServers` auto-approved `.mcp.json` servers; CVE-2026-21852 — repo-set `ANTHROPIC_BASE_URL` sent API requests with the user's key before trust. Reported Jul 21 2025; fixes Aug 26 2025 (hooks), Sep 22 2025 (MCP), Dec 28 2025 (API key) — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/). CVSS values differ between secondary sources (8.8/9.1 vs 8.7/5.3) — [borncity](https://borncity.com/win/2026/03/02/vulnerabilities-cve-2025-59536-cve-2026-21852-in-anthropic-claude-code/); [MintMCP](https://www.mintmcp.com/blog/claude-code-hooks-security)
- PromptArmor (16 Oct 2025): a malicious Claude Code marketplace plugin's hooks rewrite `settings.local.json` to permanently allow `curl` and/or auto-approve curl in a pre-tool hook (`suppressOutput` hides it); a prompt-injected "debug/docs" command exfiltrates codebase context to an attacker "RAG service"; a fake Anthropic-style GitHub account was convincing enough to get collaboration invites — [PromptArmor](https://promptarmor.substack.com/p/hijacking-claude-code-via-injected)
- Cato Networks modified Anthropic's open-source "GIF Creator" skill to download and run external code, deploying MedusaLocker ransomware (Axios, 2 Dec 2025) — [Axios](https://www.axios.com/2025/12/02/anthropic-claude-skills-medusalocker-ransomware) (search snippet)
- ClawHavoc (ClawHub/OpenClaw, Jan–Feb 2026): crypto-themed malicious skills sharing one C2; counts differ — 341 malicious skills (GoPlus AgentGuard) vs waves of 28 and 386 (OpenSourceMalware) — [AgentGuard AGS-2026-0007](https://agentguard.gopluslabs.io/advisor/AGS-2026-0007); [OpenSourceMalware](https://opensourcemalware.com/blog/malicious-clawhub-skills-target-openclaw-users)
- Snyk ToxicSkills (5 Feb 2026): 3,984 skills from ClawHub and skills.sh; 534 (13.4%) with ≥1 critical issue; 1,467 (36.82%) with ≥1 flaw of any severity; 76 confirmed malicious payloads (human-verified), 8 still live at publication; 91% of confirmed malicious combine prompt injection with malicious code; hardcoded secrets in 10.9% of ClawHub skills; daily ClawHub submissions grew from <50 (mid-Jan) to >500 (early Feb) — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub). Note: some third parties mislabel the 1,467 "flaws" as malicious.
- Academic: Liu et al. (USENIX Security 2026, arXiv:2602.06547) analysed 98,380 skills and confirmed 157 malicious (seen only via OWASP summary) — [OWASP Agentic Skills Top 10 – AST01 Malicious Skills](https://owasp.org/www-project-agentic-skills-top-10/ast01.html)
- Typosquatting (UpGuard, 2 Jul 2026): 18,000 public Claude Code settings files on GitHub contained MCP server names with typos/casing variants; 3–15 unverified lookalikes per official brand server; lookalikes are 10–16% of all MCP servers across registries studied; only 8% of 847 sampled Smithery servers had an "official" badge; HubSpot search showed nine remote servers, one official; registry sizes ~1,000 (official MCP Registry), >3,500 (Smithery), >17,000 (MCP.so) — [UpGuard](https://www.upguard.com/blog/typosquatting-in-the-mcp-ecosystem)
- Official MCP Registry ties names to verified GitHub accounts/domains (reverse-DNS namespaces, OAuth/OIDC/DNS TXT) but delegates code security scanning to the ecosystem and is in preview — [modelcontextprotocol.io registry](https://modelcontextprotocol.io/registry/about)

### Inferences
- The highest-probability threats for a small dev team are: (1) installing an unvetted skill/plugin from an open registry, (2) a lookalike/unofficial MCP server from npm/Smithery, (3) cloning a hostile repo whose `.claude/`/`.mcp.json` config runs code (now gated by trust dialog, but `-p`/CI runs show no prompt), (4) indirect prompt injection via issues/web content combined with an exfil-capable tool.
- Malicious skills are dangerous because they are both instructions (prompt injection) and code (scripts/install steps) — scanners must cover both.

### Gaps
- No public incident found of a malicious plugin in Anthropic's official `claude-plugins-official` marketplace.
- Primary Invariant tool-poisoning post and Koi postmark post not fetched directly (Koi URL now redirects).
- Liu et al. paper not verified directly.

## B2. Scanners and guardrails: mcp-scan/Agent Scan, skill scanners, sandboxing, permission deny rules, managed settings, SHA pinning

### Takeaway
Detection tools (Snyk Agent Scan, Cisco Skill Scanner) are best-effort and should be paired with prevention: Claude Code's OS sandbox for Bash, permission deny rules, `.mcp.json`/trust controls, managed allowlists for marketplaces and MCP servers, SHA-pinned plugin sources with auto-update off, and full-process isolation (devcontainer/VM) for anything run in bypass mode. Crucially, hooks, MCP servers, LSP servers and plugin monitors run **outside** the sandbox and permission system.

### Cited Findings
- Snyk Agent Scan (formerly Invariant Labs' mcp-scan; the acquisition of Invariant by Snyk in June 2025 is reported by third-party listings such as [appsecsanta](https://appsecsanta.com/mcp-scan), not the README; `invariantlabs-ai/mcp-scan` resolves to the same repo stats on shields.io; 3.2k stars, v0.6.8): auto-discovers Claude Code/Desktop, Cursor, Gemini CLI, Windsurf, Copilot, Amp, OpenClaw configs; detects prompt injection, tool poisoning, tool shadowing, toxic flows (MCP) and prompt injection, malware payloads, suspicious downloads, insecure credential handling, hardcoded secrets (skills); usage `uvx snyk-agent-scan@latest ~/.claude/skills`; `--ci`; requires `SNYK_TOKEN`; sends tool names/descriptions and skill content to Snyk's API (secrets redacted); scanning connects to/starts MCP servers, so run in a sandbox for untrusted configs and use `--dangerously-run-mcp-servers` only in trusted environments — [snyk/agent-scan](https://github.com/snyk/agent-scan); Snyk's ToxicSkills post recommends `uvx mcp-scan@latest --skills` — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)
- Cisco AI Defense Skill Scanner (2.6k stars, v2.3.0): YAML + YARA-X patterns, AST/dataflow analysis, optional LLM-as-judge, CEL decision layer; SARIF output, GitHub Action, pre-commit hook; Agent Skills spec format (Claude `.claude/commands` via `--lenient`); "No findings ≠ no risk" — [cisco-ai-defense/skill-scanner](https://github.com/cisco-ai-defense/skill-scanner); companion cisco-ai-defense/mcp-scanner 1.1k stars — [shields.io](https://img.shields.io/github/stars/cisco-ai-defense/mcp-scanner.json)
- Plugin trust model: "A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges"; components: hooks, monitors, mods (JS inside Claude Code), MCP/LSP servers, `bin/` added to PATH, skills/agents/commands as instructions; hooks/monitors/MCP/LSP/mod processes run outside the sandbox and permission rules; auto-update can change reviewed files; trust warning: Anthropic "cannot verify that they will work as intended or that they won't change"; the `claude-community` catalog pins nearly every entry to a commit SHA and refuses other commits; reserved official names are only accepted from `github.com/anthropics/` — [Claude Code docs: Plugin security](https://code.claude.com/docs/en/plugins/security)
- Anti-impersonation: marketplace names that imitate official ones (e.g. `official-claude-plugins`, `claude-plugins-v2`, non-ASCII, bidi characters, alternate spellings like `claude.code.plugins`) are refused — [Claude Code docs: Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference)
- Managed plugin controls: `strictKnownMarketplaces` (allowlist; `[]` blocks all incl. official; `owner/*` wildcards; `hostPattern`/`pathPattern` regex), `blockedMarketplaces`, `enabledPlugins: false` to block one plugin, `disableSideloadFlags` (rejects `--plugin-dir`, `--plugin-url`, `--agents`, non-SDK `--mcp-config`), `disableCommandPluginSources`, `allowManagedHooksOnly`, `strictPluginOnlyCustomization`, `pluginTrustMessage`, `syncClaudeAiPlugins: false`; OTel `claude_code.plugin_installed` / `plugin_loaded` (third-party names redacted unless `OTEL_LOG_TOOL_DETAILS=1`); cannot restrict entries inside an allowed marketplace except via `enabledPlugins: false` — [Claude Code docs: Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- Managed MCP: `managed-mcp.json` at `/etc/claude-code/` (Linux), `/Library/Application Support/ClaudeCode/` (macOS), `C:\Program Files\ClaudeCode\` gives exclusive control (`{"mcpServers": {}}` disables MCP); `managedMcpServers` (https only, no `command`); `allowedMcpServers`/`deniedMcpServers` match by `serverUrl` (wildcards), `serverCommand` (exact argv array) or `serverName` — "A `serverName` entry ... is not a security control"; `allowManagedMcpServersOnly: true` makes the allowlist authoritative; Anthropic "doesn't security-audit or manage any MCP server" — [Claude Code docs: Managed MCP](https://code.claude.com/docs/en/managed-mcp)
- Sandbox: Bash/PowerShell/Monitor commands only; Seatbelt (macOS), bubblewrap+socat (Linux/WSL2), none on native Windows; writes limited to cwd + temp; **reads default to most of the machine including `~/.ssh` and `~/.aws/credentials`** unless `filesystem.denyRead` or `sandbox.credentials` (mode `deny` also unsets env vars like `GITHUB_TOKEN`); network via local proxy with `allowedDomains` starting empty; unsandboxed retry via `dangerouslyDisableSandbox` unless `allowUnsandboxedCommands: false` ("Strict sandbox mode"); `failIfUnavailable: true` to refuse to run unsandboxed; built on open-source `@anthropic-ai/sandbox-runtime` (anthropic-experimental/sandbox-runtime, 5.6k stars, v0.0.80) — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Permission deny rules match commands "as written"; for network enforcement use sandbox network isolation; `.mcp.json` servers have their own approval prompt; `-p` sessions show neither the trust nor the MCP prompt; `ConfigChange` hooks can audit/block settings changes; recommends managed settings, VMs/devcontainers for untrusted content — [Claude Code docs: Security](https://code.claude.com/docs/en/security)
- Trail of Bits practice: run `--dangerously-skip-permissions` only with `/sandbox` plus Read/Edit deny rules for `~/.ssh/**`, `~/.gnupg/**`, `~/.aws/**`, `~/.azure/**`, `~/.kube/**`, `~/.docker/config.json`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`, `~/.config/gh/**`, edit-deny on `~/.bashrc`/`~/.zshrc`, keychains and wallets ("Without `/sandbox`, deny rules only block Claude's built-in tools — Bash commands bypass them ... Use both"); explicit `enableAllProjectMcpServers: false` because "a compromised repo could ship malicious MCP servers"; devcontainer (trailofbits/claude-code-devcontainer) or disposable droplets for full isolation — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- OWASP has an Agentic Skills Top 10 (AST01 = Malicious Skills) — [OWASP](https://owasp.org/www-project-agentic-skills-top-10/ast01.html)

### Inferences
- SHA pinning + `autoUpdate: false` is the only control that defends against a plugin turning malicious after review (the postmark-mcp pattern); scanning catches known-bad patterns but not novel or delayed payloads.
- Because hooks and stdio MCP servers bypass the sandbox, "enable the sandbox" is not sufficient protection against a malicious plugin — the review gate at install time and the managed allowlist matter more; for high-risk experimentation use a devcontainer/VM.
- Agent Scan sends skill content and tool descriptions to Snyk — teams with confidential internal skills should consider Cisco's locally-runnable scanner or Agent Scan's `inspect` mode.

### Gaps
- Whether Claude Code notifies users when an approved MCP server's tool descriptions change (rug-pull detection) was not found in docs.
- No independent precision/recall figures for Agent Scan or Cisco Skill Scanner (Cisco says it publishes per-preset metrics; not fetched).
- Pinning/lockfile behaviour of `npx skills` installs not verified.

## B3. Practical vetting checklist for a small dev team adopting a skill / plugin / MCP server

### Takeaway
Treat every skill, plugin and MCP server as third-party code with your user's privileges plus an instruction channel into the model: allowlist sources, read the executable parts, pin by SHA, scan, run with least privilege, and re-review on every update.

### Cited Findings
- Official review steps before installing a plugin: `claude plugin marketplace list` (check source), `/plugin` details "Will install" section, read `hooks/hooks.json`, `.mcp.json` and every file in `bin/`, then `claude --plugin-dir <dir> plugin details <name>` for the Component inventory; after install, `claude plugin details <name>`; on removal note cached files remain 14 days under `~/.claude/plugins/cache/` — [Claude Code docs: Plugin security](https://code.claude.com/docs/en/plugins/security)
- Check Point's recommendations: inspect `.claude/`, `.vscode/` and similar config folders before opening untrusted projects; review configuration changes in code review with the same rigor as source; treat unusual setup requirements as suspicious; keep Claude Code updated — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- Snyk's post-incident steps: scan installed skills, remove skills from flagged authors, rotate credentials reachable by skills with API/cloud/financial access, check agent memory files for tampering — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)
- UpGuard: allow only verified, trusted MCP servers; handle MCP configurations with the same care as passwords — [UpGuard](https://www.upguard.com/blog/typosquatting-in-the-mcp-ecosystem)
- Enforce MCP allowlists by `serverUrl`/`serverCommand`, never `serverName` — [Claude Code docs: Managed MCP](https://code.claude.com/docs/en/managed-mcp)
- Curated-list model with code review per addition — [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)

### Inferences
Checklist (synthesised from the findings above):
1. **Provenance**: publisher identity (official vendor org? matches domain? MCP Registry namespace verified?), repo age, stars/maintainers, recent commits; reject lookalike names (casing/typos) and anything only on open registries (ClawHub/Smithery/MCP.so) without a vendor link.
2. **Read the executable surface**: SKILL.md + `scripts/`; plugin `hooks/hooks.json`, `.mcp.json`, `bin/`, monitors/mods, `command` sources; MCP server `command`/`args`/`env`. Red flags: curl|sh, base64/obfuscated commands, downloads of binaries or password-protected zips, writes to `~/.claude/settings*.json`/shell rc/memory files, hooks with `suppressOutput`, requests for broad tokens.
3. **Read the instruction surface**: look for hidden/zero-width text, "ignore previous instructions", instructions to send data to URLs, tool descriptions that mention other tools (shadowing).
4. **Scan**: Snyk Agent Scan (`uvx snyk-agent-scan@latest <path>`, inside a sandbox) and/or Cisco Skill Scanner (pre-commit/CI); treat "no findings" as non-evidence.
5. **Pin**: add to the team marketplace with `sha` (git) or `sha256` (archive), or vendor the files; set `autoUpdate: false` for external marketplaces; MCP servers by exact versioned package (no `@latest`).
6. **Least privilege**: scoped/read-only tokens via `${VAR}`/OAuth, never secrets in committed config; avoid the lethal trifecta (private data + untrusted input + egress) in one session; sandbox on with `denyRead`/`credentials` for secrets and a small `allowedDomains`; `allowUnsandboxedCommands: false` for bypass-mode users; devcontainer/VM for experiments.
7. **Govern**: managed `strictKnownMarketplaces` + `disableSideloadFlags` + `allowedMcpServers` with `allowManagedMcpServersOnly` (Team/Enterprise), or at minimum a repo-level marketplace + PR review; keep `enableAllProjectMcpServers: false`; OTel `plugin_installed/plugin_loaded` + `OTEL_LOG_TOOL_DETAILS=1` for inventory.
8. **Re-review on change**: diff every update before bumping the pin; re-scan periodically; have a removal/credential-rotation runbook.

### Gaps
- No standard, independently validated checklist from Anthropic/OWASP for skills was fetched in full (OWASP AST Top 10 seen only for AST01).
- No data on how effective manual review is against obfuscated skill payloads.
